# Идемпотентность запросов

## Что это вообще значит

Идемпотентность нужна, чтобы один и тот же запрос не выполнился два раза.

Простой пример:

1. пользователь нажал кнопку `Перевести` один раз;
2. приложение отправило запрос;
3. сеть зависла;
4. приложение не поняло, дошёл запрос или нет;
5. приложение отправило тот же запрос ещё раз.

Без идемпотентности деньги могут списаться дважды.

С идемпотентностью сервер понимает:

- это тот же самый запрос;
- я уже его обрабатывал;
- второй раз выполнять не надо;
- нужно вернуть тот же самый ответ, что и в первый раз.

## Как это работает у нас

Клиент отправляет заголовок:

```http
Idempotency-Key: 6f9c4b7d-1b4d-4e5f-8d7c-1c2d3e4f5a6b
```

Это просто уникальный ключ запроса.

Обычно это `UUID`.

Дальше сервер делает так:

1. смотрит на `Idempotency-Key`;
2. ищет, был ли уже такой ключ у этого пользователя;
3. если не был:
   - выполняет запрос;
   - сохраняет результат;
4. если уже был:
   - не выполняет запрос заново;
   - возвращает старый результат.

## Где это уже работает

Идемпотентность включена в:

1. `AccountsService`
2. `UsersService`
3. `CreditsService`

Она применяется к внешним mutation-запросам:

- `POST`
- `PATCH`
- `PUT`
- `DELETE`

на маршрутах вида:

```text
/api/...
```

Внутренние ручки вида:

```text
/api/internal/...
```

специально не затронуты.

## Какие запросы клиент обязан отправлять с `Idempotency-Key`

Все запросы, которые меняют состояние.

Примеры:

### AccountsService

- открытие счёта
- закрытие счёта
- пополнение
- снятие
- перевод
- регистрация push token
- удаление push token

### UsersService

- блокировка пользователя

### CreditsService

- создание тарифа
- оформление кредита
- погашение кредита
- настройка автоплатежа

## Какие запросы можно не отправлять с `Idempotency-Key`

Обычные `GET`.

Примеры:

- получить список счетов
- получить профиль
- получить историю операций
- получить список тарифов

`GET` и так не должен менять состояние.

## Главное правило для frontend и mobile

Очень важное правило:

- если это **повтор того же самого запроса**, нужно использовать **тот же самый** `Idempotency-Key`;
- если это **новое действие пользователя**, нужен **новый** `Idempotency-Key`.

То есть:

### Правильно

Пользователь нажал `Перевести`.

Клиент сгенерировал:

```text
Idempotency-Key: aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee
```

Если сеть зависла и клиент повторяет **этот же самый** перевод, он должен отправить **тот же ключ**:

```text
Idempotency-Key: aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee
```

### Неправильно

Если при каждом retry генерировать новый ключ, сервер подумает, что это новый запрос, и выполнит его ещё раз.

## Что делает backend

Backend хранит для каждого запроса:

1. `Idempotency-Key`
2. пользователя
3. HTTP method
4. path
5. query string
6. hash тела запроса
7. статус ответа
8. тело ответа

Если приходит тот же ключ и тот же самый запрос, backend возвращает тот же ответ.

Если приходит тот же ключ, но другой запрос, backend отвечает:

```http
409 Conflict
```

Пример ответа:

```json
{
  "title": "The same Idempotency-Key was already used for a different request.",
  "status": 409
}
```

## Если клиент забыл передать `Idempotency-Key`

Тогда backend отвечает:

```http
400 Bad Request
```

Пример:

```json
{
  "title": "Idempotency-Key header is required for this request.",
  "status": 400
}
```

## Что происходит при ошибке `500`

Если запрос завершился серверной ошибкой `500`, такой результат не кэшируется как успешный идемпотентный результат.

Это сделано специально:

- если запрос упал;
- клиент может безопасно повторить его тем же ключом;
- backend попробует выполнить его заново.

## Примеры запросов

### Пример 1. Пополнение счёта

```http
POST /api/accounts/deposit
Authorization: Bearer <token>
Idempotency-Key: 7d2dc7dc-f0c4-4c27-b67f-6d2f5d5d7f11
Content-Type: application/json
```

```json
{
  "accountId": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaa3",
  "amount": 1000
}
```

### Пример 2. Повтор того же запроса

Нужно отправить абсолютно тот же запрос:

- тот же `Idempotency-Key`
- то же тело
- тот же маршрут

Тогда сервер не сделает повторную операцию, а просто вернёт сохранённый ответ.

### Пример 3. Ошибка использования ключа

Нельзя делать так:

1. сначала отправить

```json
{
  "accountId": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaa3",
  "amount": 1000
}
```

2. а потом с тем же ключом отправить

```json
{
  "accountId": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaa3",
  "amount": 2000
}
```

В этом случае сервер вернёт `409 Conflict`.

## Что нужно сделать frontend

Для web-клиента правило простое:

1. перед каждым `POST/PATCH/PUT/DELETE` генерировать UUID;
2. класть его в header `Idempotency-Key`;
3. если это retry того же запроса, использовать тот же ключ;
4. если это новое действие пользователя, генерировать новый ключ.

## Что нужно сделать mobile

Для Android/iOS правило абсолютно то же самое:

1. при создании mutation-запроса генерировать UUID;
2. отправлять его в `Idempotency-Key`;
3. при retry использовать тот же ключ;
4. не переиспользовать старый ключ для новой операции.

## Очень коротко

Нужно запомнить только это:

1. любой запрос, который что-то меняет, должен идти с `Idempotency-Key`
2. повтор того же запроса = тот же ключ
3. новое действие = новый ключ
4. если ключ забыли, сервер вернёт `400`
5. если тем же ключом отправили другой запрос, сервер вернёт `409`
